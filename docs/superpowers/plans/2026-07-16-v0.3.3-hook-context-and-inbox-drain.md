# v0.3.3 — Hook Context Delivery & Inbox Drain (patch release)

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Fix the two most consequential message-delivery bugs surfaced during v0.3.2 field use, plus one high-signal PreCompact context-bloat cleanup. All three were noted as "deferred to v0.3.3" in the v0.3.2 SDD ledger; #28 was filed on 2026-07-16 after v0.3.2 shipped and turned out to be more severe than #27. This is a patch release — no new features, no protocol changes, no CLI surface changes.

**Issues addressed:**

- **#28** (Critical) — PostToolUse path in `check-inbox.sh` silently drops messages because Default mode emits via `systemMessage` (terminal-only) instead of `hookSpecificOutput.additionalContext` (reaches model). One field-reported instance cost ~10 hours on a time-sensitive decision. Symptom is asymptomatic to sender (message CLAIMED + archived to `.delivered/` + logged) and asymptomatic to recipient's inbox (already archived, shows nothing pending).
- **#27** (Important) — SessionStart hook fires `check-inbox.sh --summary-only` which emits a `pending: N` summary but doesn't drain the queue. The agent's reflex first-turn `/bridge standby` invocation buries any pre-queued directive under the standby wait-loop. v0.3.2 shipped interim SKILL.md guidance (Task 8 Workstream B); this closes the architectural fix.
- **v0.3.2 ledger follow-up** — `check-inbox.sh --summary-only` enumerates every non-resolved conversation on PreCompact. With hundreds of accumulated "waiting" threads from old sessions, this dominates injected context on every `/compact`. Small filter (~50 LOC), no protocol impact.

**Primary audience:** As with v0.3.2, the runtime consumers are agents (orchestrator + specialists in the running plextura-suite deploy), not human operators. Every fix here changes agent-visible behavior: whether pre-queued messages reach the model (task 1), whether they get drained before standby (task 2), whether the PreCompact injection is manageable (task 3). No new SKILL.md subsections are needed — the fixes restore behavior agents already expect from the current SKILL text.

**Architecture:** No new lib modules. All three fixes are surgical modifications to existing scripts:

- Task 1: rewrite the emission branch of `check-inbox.sh` (lines ~228 and ~406–414) to route through `hookSpecificOutput.additionalContext` where supported.
- Task 2: add `--drain` mode to `check-inbox.sh` that surfaces each pending message individually as an actionable turn-input, wire it into SessionStart in `hooks.json`, refuse `bridge-listen.sh` launch while pending > 0.
- Task 3: add `--stale-conv-days N` filter (default 30) to `check-inbox.sh --summary-only`'s conversation-enumeration block.
- Task 4: release-bookkeeping.

**Tech Stack:** bash, jq, existing 543-test bash test suite under `plugins/session-bridge/tests/`.

Claude Code's hook output JSON supports different shapes per hook event. Empirically observed from the v0.3.2 codebase and Claude Code docs (verify against current docs in Task 1 Step 1):

|--------------------|--------------------------------|-------------------------------------------------------|
| `SessionStart`     | No (terminal only)             | Yes                                                   |
| `UserPromptSubmit` | No (terminal only)             | Yes                                                   |
| `PostToolUse`      | No (terminal only)             | **Unverified — Task 1 Step 1 must confirm**           |

## Task 1: Fix #28 — route Default and Summary-only modes through additionalContext

Rationale from issue #28: `check-inbox.sh`'s Default mode emits claimed messages via `systemMessage`, which reaches the terminal but not the model's context. The Stop-hook path correctly uses `hookSpecificOutput.additionalContext`. PostToolUse never got the same treatment. Messages CLAIMED, archived to `.delivered/`, logged as delivered — but the agent never sees them. Sender sees success, recipient's inbox shows nothing pending because it's already archived.

The v0.3.2 CLAIM/OUTPUT logging + `.delivered/` archiving (from #17's fix) is the only reason this bug is even detectable. Task 1 closes the emission gap without touching the archival semantics.

Detection gap flagged in #28: archival is gated on `jq`'s exit status, not on whether the message reached the model. `jq` succeeds whenever it prints valid JSON regardless of which field carries the payload — so there's no error path that distinguishes real delivery from silent drop. Task 1's test coverage must include an assertion that catches this specific mode.
